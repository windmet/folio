## 0. 总结

当前网站的**事件骨架总体可靠**：人物出场、Space 技术线、俄罗斯章鱼烧、《俺知》制作复盘、昼夜 cast 关系、后半 Karaoke 与真正 Ending，大部分已经和多轮复核后的语料一致。

目前真正需要处理的主要不是“整站事实都错”，而是四类问题：

1. **硬事实错误**：目前确认 2 个根问题。
   - Amazon 5000 円 Bingo 把濱健人误写成中奖者。
   - 汐谷文康的读音写成 `しおや ふみやす`，应为 `しおや ふみよし`。
2. **一处错误向多条故事线扩散**：濱的 Amazon 误判同时污染 Bingo thread 与「ギャラ飲み」人物线。
3. **人物 aliases 字段混层**：18 人共 19 条现有 aliases 中，至少 **10 条只是「さん／君」敬称变体**，不应和「ふーみん／コマッチ／トシピ」处在同一语义层。
4. **读者语言仍带编辑台 / 数据模型味道**：
   - 现有自动 reader-copy audit 抓到 **43 Event + 9 Thread = 52 个候选**，但其中很多只是隐藏的 `qualification`，并不直接污染页面。
   - 人工再审后，当前至少有 **11 / 16 条 Thread 正文**仍明显在讲“我们如何整理资料”，而不是讲故事；另有 2 条轻度偏编辑口吻。
   - 至少 **8 个核心 UI 组件**仍直接显示 `SETUP / DEVELOPMENT / PAYOFF / NATIVE CLOCK / CURRENT SOURCE / EVENT / THREAD / PERSON` 等数据模型语言。
   - 至少 2 个 Event 可见文案仍把校对流程带给读者：Bingo 的“规则 patch”、杯类奖品“不是早先误听成的挂毯”。

## 1.2 最新证据链

### A. 佐藤祐吾已经在上一轮退出

蛋白质 12-pack：

- 57 番
- **佐藤祐吾**
- 奖品刚公布就直接 Bingo

因此 Amazon 5000 円的第二人**不应再算佐藤祐吾**。

### B. Amazon 轮明确是“两人刚好同时”

23 番时：

> 「俺を知ってくれ！」
> 「俺を知ってくれ！」
> 「丁度！」
> 「じゃあ、丁度Amazonギフトカード2名様です！」

其中寺島惇太可以直接锁定。

### C. 濱不是中奖者，而是在抢寺島的卡

粉丝评论时间轴有两个非常直接的旁证：

> `4:05:24 惇太さんのアマギフ盗もうとする濱健人`

以及：

> `4:05:26 アマギフ強奪濱さん`

实时 Chat 在这一秒大量刷：

> `濱さんwww`
> `惇太さん用ww`
> `惇太さん嬉しそう`

这里的「濱www」是因为**抢卡动作**，不是因为濱中奖。

### D. 最后两名未中主奖者应是矢野＋濱

所有主奖结束：

> 「あれ？あれ？あれ？2人。」
> 「サングラス返してもらっていいですか？」

矢野明确是未中奖者之一。

随后：

> 「もちろんお二人にも参加賞があります。」
> 「Amazon1000円分！」

并出现对濱的递交 / 收钱反应，粉丝时间轴更直接记为：

> `4:10:38 「ギャラ+1000円いただいてすいません」`

所以濱应是另一名**没有拿到任何主奖、最后领取 1000 円参加赏的人**。

### E. 参与者消元

Bingo 主体参与者可整理为：

- 狩野翔
- 濱健人
- 汐谷文康
- 井上雄貴
- 寺島惇太
- 光富崇雄
- 堀金蒼平
- 佐藤祐吾
- 熊谷俊輝
- 矢野奨吾

已确认非 Amazon 的主奖中奖者：

- 汐谷文康
- 光富崇雄
- 佐藤祐吾
- 井上雄貴
- 熊谷俊輝
- 狩野翔

最后仅拿参加赏：

- 矢野奨吾
- 濱健人

因此 Amazon 两名只能剩：

- **寺島惇太**
- **堀金蒼平**

### 结论

> **OVERRIDE：Amazonギフトカード 5000円分 × 2 的中奖者采用「寺島惇太＋堀金蒼平」。**

置信度建议拆开：

- 寺島惇太：**A**
- 堀金蒼平：**B+ / A-**

如果网页希望严格表达证据等级，可以给堀金加一条自然 reader note：

> 第二位中奖者在当秒没有被清晰点名；按此前中奖者与最后参加赏两人的排除关系，指向堀金蒼平。

不要再把濱写成中奖者。

# 5. P1｜Aliases / “别称”字段需要重新定义

## 5.1 当前问题

当前 schema 只有：

```text
aliases: string[]
```

但这个数组同时被：

1. Person panel 显示为 **「本场别名」**
2. 搜索索引用于事件 / 人物检索

于是三种完全不同的东西混在一起：

### 真正昵称

- コマッチ
- ふーみん
- 濱ちゃん
- トシピ

### 本场常用名字简称 / 呼び名

- 惇太
- 修
- 宗悟
- 祐吾
- 蒼平
- ハマ

### 纯敬称变体

- 狩野さん
- 井上君
- 伊藤さん
- 光富さん
- 熊谷君
- 観世君
- むろさん
- 清典さん
- 山本さん
- 矢野さん

这三类不应在读者界面被统称为“别称”。

---

## 5.2 `さん／君` 要不要加入 aliases？

### 结论：原则上不要

`○○さん / ○○君`：

- 不构成独立昵称；
- 几乎没有人物消歧价值；
- 会使页面看起来像机器从 transcript 自动抽取 address form；
- 如果为了搜索「熊谷君」也要能搜到熊谷，应该由**搜索正规化**处理，而不是人工给每个人维护敬称排列组合。

因此不要继续扩充：

> `狩野さん / 狩野君 / 翔さん / 翔君 ...`

这种组合。

它会无限膨胀且没有编辑价值。

---

## 5.3 推荐字段语义

### 最优方案

拆成：

```text
aliases
```

只保存**读者可见、具有识别意义的昵称 / 特殊称呼**。

另加：

```text
searchAliases
```

只进入检索，不显示。

或者更明确：

```text
nicknames
callNames
searchAliases
```

### 如果暂时不改 schema

至少把页面标签：

> `本场别名`

改成：

> **本场常用称呼**

并删除所有纯 `さん／君` 变体。

# 6. P1｜室元気：“账号”与“人物”在 UI 上仍会被合并

而不是：

> 室元気

### 这里的不确定性必须保留

这是少数**会改变人物身份判断**的低置信度点，因此可以保留自然 reader note：

> 这段只能确认使用的是室元気的账号，实际说话者未确认。

# 20. 最终判断

这个站点现在**不需要推翻重做内容架构**。

数据模型已经把：

- 三条媒体时间轴
- Event
- Thread
- Person
- Source
- 《俺知》昼夜 cast / 制作
- Space remote / account

分得相当清楚。

现在最需要的是一次真正的 **semantic/editorial pass**：

> **让内部严谨继续留在数据层，让读者看到的是故事；只有会改变“谁做了什么”的不确定性，才走到前台。**

这次 Amazon Bingo 正好是最典型的例子：

旧版本为了完成闭环，把 Chat 的「濱www」解释成“濱中奖”，于是制造出一个看起来很漂亮但实际错误的“空手来→中大奖→ギャラ飲み”故事。

重新把评论时间轴、Chat、中奖顺序和参加赏一起放回去以后，真正的故事反而更好：

> **濱一路想拿东西，却偏偏没中主奖；看到寺島拿 Amazon 卡就直接伸手去抢，最后只拿到 1000 円参加赏，再自己说成「ギャラ＋1000円」。**

语义 patch 的目标应当就是把这种“证据更准确以后，故事反而更自然”的版本带回网站。
